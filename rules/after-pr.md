# PR 후 — 판정 기록

PR 후 판정을 기록하는 법이다. `dev-workflow` 스킬 안에만 있던 동안 한 번도 안 떠서 rules에 둔다.
착수 전은 `rules/before-work.md`, 시점 없는 문제 발견은 `rules/problem-found.md`다.

**장부는 작업 위치마다 하나다.** 두 곳에 쓰면 언젠가 갈린다.

| 작업 위치 | PR 판정 장부 | 보이는 곳 |
| --- | --- | --- |
| `~/prv` | **각 레포 `docs/decisions.md`** | GitHub |
| `~/plab`·`~/work` | `~/.claude/judgment-log-work.md` | 로컬만 (git 추적 안 됨) |

`~/.claude/judgment-log.md`는 PR 판정 행을 더 받지 않는다(2026-09-30 이전 `~/prv` 9행만 남아 있다).
`## 문제 발견` 표만 계속 쓴다. `~/.claude`가 PUBLIC repo라 회사 관련 문제 발견은 `judgment-log-work.md`에
적는다. 아래에서 「판단 로그」는 위 표의 장부다.

## 완료 신호 — 판단 로그 트리거의 전제

**완료 = `orch ls`가 `done` + 워크트리 `git status --porcelain`이 빈 것.** PR URL이나 Notion `PR` 칸이
찼다고 완료가 아니다.

- ralph 루프는 PR을 만든 뒤에도 리뷰 지적을 커밋으로 얹는다(PR 생성 후 8분 넘게 이어진 적이 있다).
  orch가 `running`인 동안 PR을 리뷰하지 않는다
- PR 본문의 테스트 수·통과 기준 표는 루프의 주장이지 완료 증거가 아니다

## 판단 로그 — PR 게이트

**트리거는 상태다. 스킬 호출 여부와 무관하다.** orch 태스크가 `done`이고, 그 PR이 열려 있고, 워크트리가
빈 것을 확인한 직후다. `orch ls`를 직접 친 경우도 포함된다.

- main/dispatcher 세션에서만 띄운다(ralph 세션은 헤드리스라 못 한다)
- 장부에 그 PR 행이 이미 있으면 건너뛴다. 여러 번 들어와도 안전해야 한다
- 워크트리가 더러우면 블록을 띄우지 않고 그 사실만 말한다. 이미 바뀐 사실 위에 쌓은 판단은 로그가 없는
  것보다 나쁘다 — 틀린 근거가 기록으로 남는다
- 사실은 main이 직접 모은다(`gh pr view`, `git -C <worktree> diff --stat main...HEAD`, PR 본문의 Pre-PR 출력)

**두 층으로 나눈다.** 화면 블록에는 판정에 쓰는 것만 둔다(30줄 안쪽). 나머지는 상세 파일에 쓰고 블록
맨 아래에 경로 한 줄로 남긴다.

- 상세 파일: 블록을 쓰는 세션 scratchpad의 `gate-<ID>-detail.md`. 워크트리에 만들지 않는다(커밋에 들어간다).
  경로는 `/`로 시작하는 절대 경로 전체를 쓴다
- 상세 파일에 넣는 것: 측정값 정의, 자동 기준 전체 대조, 실패 징후 전부(안 나타난 것도 측정값과 함께),
  리뷰가 안 고친 것 전부와 이유 원문, 확인만 한 것(CI·테스트·리뷰 건수·변경 범위·도메인 4줄).
  won't-fix·defer는 「무엇이 깨지나」 한 줄을 지우지 않는다. 상세 파일은 줄일 필요가 없다

### 화면 블록

코드 블록으로 감싸지 않고 마크다운으로 그대로 띄운다.

```markdown
## <ID> — PR #<n> <title>

- 왜: <이 티켓이 막거나 여는 것 한 문장. plan·design 목적 문장에서 가져온다>
- 한 일: <무엇을 바꿨나 한두 문장. 함수·파일 이름이 아니라 동작으로 쓴다>
  <반려 뒤 재판정이면: 반려 이유(jw 원문), 바꾼 것, 반려 전 값과 지금 값>

**jw 기준**: 「<plan `## jw 기준` 원문 그대로>」

**기준을 세운 사례**: <plan `## jw 기준`의 「기준을 세운 사례」 한 줄>
- 변경 전: <그 사례가 어떻게 나왔나. 실제 값으로>
- 변경 후: <이번 PR 뒤 같은 사례가 어떻게 나왔나>

<jw 기준을 잰 원래 숫자 표. 원래 숫자가 표에 안 들어갈 만큼 많으면 문장과 사례 하나로 쓴다>

- 결과: <표에서 어느 칸을 보면 되는지 한 줄. 판단어 없이>
- plan 구간:
  - 측정값: <구간 조건에 대응하는 값>
  - 통과: <조건>
  - 다시 잰다: <조건>
  - 미완: <조건>   ← 어느 구간인지 고르지 않는다

**판정 전에 알 것**
- <조건 이름>: <한 문장. 사례가 있으면 괄호에 하나>
- 나머지(<상세 파일에 무엇이 몇 건>): <상세 파일 절대 경로>

**판정**: ___ 　**이유**: ___
```

**기준을 세운 사례 줄을 숫자 표보다 먼저 쓴다.**

- 그 사례를 직접 찾아 변경 전·후 실제 값을 적는다. 측정 표가 그 사례를 세지 않았으면 그 사실을 이 줄
  맨 앞에 쓴다(`이 측정은 기준을 세운 사례를 세지 않았다`)
- plan에 그 사례가 「없음」이면 `기준을 세운 사례: 없음`, plan에 그 줄이 없으면 `기준을 세운 사례: plan에 없음`
- 왜: 2026-11-16 #180에서 jw 기준의 「정보가 없음」을 Claude가 「프로필 칸이 빈 것」으로 좁혀 집계한 「변경 전에도
  0」이 블록에 그대로 나갔다. 실제로는 기준을 세운 사례(더샵 분당하이스트)가 변경 전에 걸려 있었다

**판정 전에 알 것에 올리는 조건.** 아래 다섯에 걸리면 반드시 올리고, 아니면 상세 파일로 보낸다.
무엇을 띄울지 Claude가 고르지 않게 하려는 것이다.

1. 실패 징후: 나타났거나 판정할 수 없는 것
2. 자동 기준: ✗이거나 판정 불가인 것
3. 리뷰 push-back: 지적과, 리뷰 세션이 안 고친 이유를 쉬운 말로
4. 데이터를 쓰는 defer: 데이터를 쓰거나 지우는 won't-fix·defer
5. 숫자 읽는 법: 결과 숫자를 읽는 법을 바꾸는 사실. 예: 측정이 구현과 같은 규칙을 옮겨 써서 같이 틀릴 수
   있다, 측정 데이터가 규칙을 다듬는 데 쓴 데이터다, 결과의 대부분이 한 종류에서 나왔다

- 항목은 조건 이름으로 시작하고 한 문장으로 끝낸다. 설명이 더 필요하면 상세 파일에 쓴다
- 걸린 것이 없으면 「없다」 한 줄을 쓴다. 그때는 jw 기준만 보고 `통과` 한 단어로 판정할 수 있다
- 자동 기준은 ✗가 없으면 띄우지 않는다. jw 기준이 위다(#97: 자동 기준 10/10인데 `impacted 0`)
- 판정값·축처럼 목록이 있는 개념을 블록에 썼는데 repo `docs/concepts.md`에 그 행이 없거나 낡았으면 맨
  아래에 `개념 표에 없음: <이름>`을 적는다
- 흐름 그림 도구가 실패했으면 그 오류를 맨 아래 한 줄로 적는다

### 쓰는 법

기준 독자는 plan과 앞 티켓을 열어 보지 않은 jw다. 블록을 쓰는 세션은 앞 티켓을 다 거쳐서 자기한테
당연한 것을 생략한다.

1. **결론 먼저, 한 문장에 사실 하나.** 문장마다 주어와 서술어를 갖춘다. `→`·`/`로 문장을 잇지 않는다.
   불릿은 2단계까지
2. **새 이름을 짓지 않는다.** 무엇을 셌는지 문장으로 쓴다. 이름으로 써도 되는 말은 jw 기준 원문, repo
   `docs/concepts.md` 용어 절, 도구·리포트에 실제로 찍히는 글자뿐이다. plan·코드의 줄임말(`M1`·`tp`)과
   다른 티켓 번호로 설명을 대신하지 않는다. 그 repo의 단계 이름은 흐름 그림의 노드 이름 그대로 쓴다
3. **숫자에는 비교 대상과 세는 방법을 붙인다.**
   - 다른 방법으로 집계한 두 숫자를 같은 이름으로 부르지 않는다. plan이 정의한 측정값 이름은 plan 정의로 집계한 값에만 붙인다
   - 같은 측정을 여러 번 돌렸으면 값마다 어느 실행인지 쓴다. 숫자를 쪼개면 합이 어떻게 맞는지 쓴다
   - 평균·범위 같은 가공한 값보다 원래 숫자 표를 먼저 둔다
4. **설명마다 그 PR 데이터의 실제 사례 하나.** 코드 이름은 동작을 쓴 뒤 괄호에 넣는다
5. **누가 했는지 주어를 쓴다.** 구현 루프 · 리뷰 세션 · main(블록을 쓰는 세션)은 다른 주체다
6. **판단어를 넣지 않는다.** 개선·안정적·문제없음이 들어가면 그 줄이 판정이 된다

```
✗ 깨지는 버전이 134/134 지점에 붙었고 다른 곳은 0이다
✓ 버전을 적어야 하는 코드 줄 134개 모두에 「Django 몇 버전에서 깨짐」이 적혔다.
  측정 스크립트가 따로 다시 계산해 맞춰 보니 다르게 적힌 줄은 0개였다
```

### 블록을 읽는 법 — jw가 판정할 때

| jw 기준 | 자동 기준 | 보통의 판정 | 쓸 것 |
| --- | --- | --- | --- |
| 충족 | 전부 ✓ | 통과 | `통과` 한 단어 |
| 충족 | ✗ 있음 | 그 ✗에 따라 반려 또는 유보 | 판정 + 이유 한 줄 |
| 미달 | 전부 ✓ | 반려 또는 유보 | 판정 + 이유 한 줄. 가장 중요한 칸 |
| 못 읽겠다 | — | 유보 | `유보` + 후속 티켓 번호 + 무엇을 다시 잴지 |

- 셋째 줄(jw 기준 미달 + 자동 기준 통과)이 이 장치를 만든 이유다. #97이 이 경우였다

- **이 표는 jw가 읽는 법이다.** Claude는 표의 어느 줄에 해당하는지 말하지 않는다
- **게이트에서 jw가 사실을 물으면 첫 문장이 답이다.** 예/아니오로 물으면 첫 단어가 예/아니오다. 배경은 그
  아래에 쓰고, 「그러니 통과가 맞다」 같은 판정 쪽 말은 하지 않는다
- 끝까지 내용이 안 잡히면 그것도 판정 재료다 — `유보 / 무엇이 바뀌었는지 이해 못 함 — #NN에서 다시`

| 티켓 성격 | 4줄 |
| --- | --- |
| 백엔드·API | 서버 부팅 / 신규 env / 마이그레이션 / 롤백 절차 |

### 흐름 그림 — 매 게이트에 블록보다 먼저 두 장

| 그림 | 담는 것 | 크기 |
| --- | --- | --- |
| **핵심 그림** | jw 기준을 어떻게 쟀는가. 블록의 「결과」 숫자가 나온 경로만 그린다 | 단계 5개 안팎 |
| **전체 흐름** | 그 repo의 입력부터 최종 출력까지. 이 PR이 바꾼 단계에 표시를 단다 | 제한 없음 |

둘 다 `archify`로 그리고 핵심 그림 → 전체 흐름 → 블록 순서로 보낸다. 그림과 블록이 어긋나면 블록을 따른다.

**그림의 글자에도 §쓰는 법 1~6을 적용한다.** 그림은 블록보다 먼저 읽혀서, 그림에서 막히면 블록도 안 읽힌다.

- 상자 이름과 설명은 동작으로 쓴다. 코드 이름·파일 이름·규칙 번호·티켓 번호는 상자에 쓰지 않고 `sources`에만 건다
- 측정값 이름은 블록 표의 줄 이름과 같게 쓴다. plan 측정값에 「jw 기준」이라는 이름을 붙이지 않는다
- 예: #180 핵심 그림은 상자 이름이 `judge_one`·`eligible_guard`·`missing_cells`였고, 설명에 「#80·#82 그대로」·「결손
  분석 두 목록」이 있었다. plan 측정값 상자 이름이 「jw 기준」이었다

- **핵심 그림**: 비교하는 두 쪽(예측·정답 등)을 나란히 두 줄(lane)로 놓고 마지막 비교 단계에서 만나게 한다.
  상자에는 제목 한 줄과 짧은 설명 한 줄만 넣고, 비교 단계 설명에 블록의 「결과」 숫자를 그대로 쓴다.
  PR마다 새로 그리고 repo에 쌓지 않는다
- **전체 흐름**: 바뀐 게 없는 PR에도 보낸다. 결과 숫자를 만든 측정 과정도 별도 줄로 넣는다
  - `docs/flow.archify.json`에 쌓고, 다음 게이트는 그 파일에서 시작한다. `~/prv`는 판정 커밋과 같이 PR 브랜치에
    커밋하고, 회사 repo는 커밋하지 않고 `.git/info/exclude`에 넣는다
  - 종류는 `workflow`. 노드마다 `tag`(`새로 생김`·`조건 바뀜`·`주기 바뀜`·`범위 좁아짐`·`그대로`·`없어짐`)를 단다.
    archify가 `tag`를 그리지 않으므로 `sublabel` 앞에 `[새로]`·`[바뀜]`·`[없어짐]`을 글자로 붙이고, 「읽는 법」
    카드에 무엇 대비 바뀐 것인지 적는다
  - 없어진 단계는 `없어짐`을 달아 맨 아래 `variant: exception` 줄에 두고 대신 들어온 노드로 화살표를 긋는다.
    그 줄에는 실패 경로도 그리므로 없어진 단계는 줄이 아니라 꼬리표로 구별한다
  - 노드마다 `sources`(파일·줄)를 걸고 `meta.repository`에 PR head 커밋을 넣고, `finalize`에 `--repo-root <워크트리>`를 준다
- **HTML·PNG는 scratchpad에 둔다.** 워크트리에 두면 커밋에 들어간다. claude.ai 아티팩트로 올리지 않는다
- **PNG로 보낸다.** jw는 휴대폰으로 볼 때가 많다. 블록에는 그림 경로를 쓰지 않는다
  ```bash
  "$HOME/.claude/tools/archify-png/archify-png" <out.html> <out.png>
  ```
  - `SendUserFile`에 `display: "render"`로 한 장씩 보낸다(`attach`는 휴대폰 앱에 안 보였다)
  - 잘렸는지는 하위 에이전트에게 Read로 열어 보게 하고 결과만 받는다. 게이트 세션이 PNG를 직접 Read하면
    휴대폰 앱에 같은 그림이 두 번 뜬다
  - 도구가 오류로 끝나면 Chrome으로 직접 찍어 보내지 않고, 블록 맨 아래에 오류를 적는다
- **자동 검사를 통과 못 해도 그림은 낸다.** 한 번 고쳐서도 `finalize`가 실패하면 검사를 건너뛰는 `render`로
  그리고, 실패한 검사 이름과 값을 블록 맨 아래에 적는다. 그림 때문에 게이트를 붙잡지 않는다
  ```bash
  node <archify>/bin/archify.mjs render workflow <candidate.json> <out.html> --repo-root <워크트리>
  ```

## jw 기준의 출처와 판정

**jw 기준과 기준을 세운 사례는 plan 맨 위 `## jw 기준`에서 그대로 가져온다.** 받는 절차는 `rules/before-work.md`
§착수 전 한 줄. 게이트에서 묻거나 다듬지 않는다.

- plan에 없으면 그 사실을 첫 줄에 적는다(`jw 기준: plan에 없음`). 지어내지 않는다
- 어긋났는지는 jw가 판정한다. 후하게 세는 것이 이 기록의 유일한 실패 방식이라, jw 기준 아래에는 값만 적는다
- 게이트는 새 판단을 내리는 자리가 아니라 plan에 이미 적은 판단과 결과를 나란히 놓는 자리다

**증거와 출처**

- 증거는 위치로 적는다(`VERIFICATION.md:169-176`, 커밋 `a0d3600`, `543 passed`). 「확인함」·「충족」은 판정이다
- 실패 징후는 측정값과 plan 임계값을 나란히 적는다. plan에 임계값이 없으면 나타남·없음을 고르지 않고
  `판정 불가`로 적는다(#91: 「뭉침이 재현되면 의심」, 실제 `spread 0.1626`). 통과 기준·실패 징후가 비어 있으면
  첫 줄에 `통과 기준: plan에 없음 — 대조 불가`
- 루프가 쓴 주장과 GitHub에서 읽은 값을 구분한다. `CI 체크`는 루프가 건드릴 수 없는 유일한 값이고, 둘이
  어긋나면 그것이 가장 중요한 사실이다
  ```
  테스트  557 passed (PR 본문 주장, CI 미확인)
  테스트  557 passed (CI checks green)
  ```
- 리뷰가 안 고친 것은 Phase C 리뷰 세션이 쓴 파일에서 가져온다. push-back을 정당한 반론으로 볼지는 jw가 정한다
- 수치에는 비교 대상을 붙인다. 순서는 plan 임계값 → 직전 티켓 측정값 → baseline이고, 셋 다 없으면
  `(baseline 없음 — 첫 측정)`. 「비교 불가」도 판정 재료다
- `✓`는 기계로 확인되는 기준(테스트 통과·파일 존재)에만 붙인다. `precision이 baseline보다 낫다`에 붙이면 판정이 된다

**판정은 3택이다. 판정마다 다음 행동이 하나로 정해져 있다.**

| 판정 | 뜻 | PR | 다음 |
| --- | --- | --- | --- |
| 통과 | 결과를 받아들인다 | 머지 | 끝 |
| 반려 | 이대로는 안 받는다 | 머지 안 함 | jw가 고른다: ① 같은 PR에서 고친다(plan에 Task 추가 → 루프 다시) ② PR을 닫고 티켓을 되돌린다. 반려 직후 한 번 묻는다. `★ADR후보` 태그 — 주 1회 그중 하나를 ADR로 올린다 |
| 유보 | 지금 정보로는 못 정한다 | 머지해도 된다 | **후속 티켓 필수.** 무엇을 어느 티켓에서 다시 잴지 이유 칸에 번호로 적는다 |

- 후속 티켓 없는 유보는 조용한 통과다. 번호가 없으면 받지 말고 되묻는다
- 되돌리기 어려운 변경(스키마·데이터 삭제)이면 유보가 아니라 반려다
- 후속 티켓에서 다시 잰 뒤 원래 행을 고치지 않는다. 후속 행 이유 칸에 `#96 유보 → 통과`처럼 잇는다
- **근거를 제안하거나 대신 채우지 않는다.** 그 빈칸이 유일하게 사람 몫이라 이 로그가 있다

**장부에 적는다.** jw가 한 단어로 답한다(`통과`). 갈렸으면 이유 한 줄을 붙인다.

- `~/prv`: PR 브랜치에서 `docs/decisions.md`의 그 티켓 행에 결과·판정·이유를 채우고 README `## 판단 기록` 절도
  고쳐 커밋·push한다. 서식은 `rules/before-work.md` §레포에 남기는 판단 기록
- 회사: `~/.claude/judgment-log-work.md`에 7열 한 행을 append한다 —
  `| 날짜 | 티켓 | jw 기준 | 결과 | 판정 | 본 것 (사실) | 근거 |`
  - `본 것`에는 자동 기준 요약과 나타난 징후만 적는다(`자동 5/5 ✓ · ⚠unknown 0 vs 임계 >0(VERIFICATION.md:169)`).
    표에서도 수치에 비교 대상을 붙이고, CI와 PR 본문이 어긋났으면 남긴다. 형식이 흔들리면 시계열로 비교할 수 없게 된다
- `스킵` → 판단 칸을 빈 채로 append한다. 재촉하지 않고 나중에 채우지도 않는다
- 여러 건이 동시에 끝나면 압축해 나열하고 한 줄로 전부 받는다(`7133 통과 / 7150 반려 드롭컬럼 롤백없음 / 7161 스킵`)
- 판단 먼저, 티켓 정리는 나중이다. diff가 신선할 때 판단한다
