# PR 후 — 판정 기록

**여기 있는 이유 — 항상 컨텍스트에 있어야 하기 때문이다.** 이 규칙들이 `dev-workflow`
스킬 안에만 있던 동안 한 번도 뜨지 않았다. 스킬은 호출해야 로드되고, 임의 PR 리뷰
세션(`ops:github-pr-review` 등)은 자신이 "게이트"에 있다고 인식하지 않는다.

개발 파이프라인 자체는 `dev-workflow` 스킬에 있다. 이 파일은 **PR 후** 판정을 기록하는 법만
담는다. 착수 전은 `rules/before-work.md`, 시점 없는 문제 발견은 `rules/problem-found.md`다.

**장부는 작업 위치마다 하나다** (2026-09-30부터). 두 곳에 쓰면 언젠가 갈린다.

| 작업 위치 | PR 판정 장부 | 보이는 곳 |
| --- | --- | --- |
| `~/prv` | **각 레포 `docs/decisions.md`** | GitHub |
| `~/plab`·`~/work` | `~/.claude/judgment-log-work.md` | 로컬만 (git 추적 안 됨) |

`~/.claude/judgment-log.md`는 **PR 판정 행을 더 받지 않는다.** 09-30 이전 `~/prv` 9행은 그대로
두고(옮기지 않는다), `## 문제 발견` 표만 계속 쓴다. `~/.claude`가 PUBLIC repo라서 회사 관련 문제
발견은 `judgment-log-work.md`에 적는다(`rules/github.md` §회사 repo에 커밋하지 않는 것).

아래에서 「판단 로그」라고 쓴 곳은 위 표의 장부로 읽는다. 중복 확인도 그 장부에서 한다.

## 완료 신호 — 판단 로그 트리거의 전제

**완료 판정 = `orch ls`가 `done` + 워크트리 `git status --porcelain`이 빈 것.**
PR URL이나 Notion `PR` 컬럼이 찼다고 완료가 아니다.

- ralph 루프는 **PR을 만든 뒤에도 계속 일한다.** 커밋 전 `superpowers:requesting-code-review`,
  PR 생성 후 `pr-review-toolkit:review-pr`을 돌려 지적사항을 추가 커밋으로 얹는다.
  실측: PR 생성 후 8분 넘게 작업 지속.
- orch가 `running`인 동안 PR을 리뷰하지 말 것 — 리뷰 도중 커밋이 얹혀 대상이 어긋난다.
- **산출물이 그럴듯할수록 확인을 건너뛰기 쉽다.** PR 본문에 테스트 수와 통과 기준 표가
  있어도 그건 루프의 주장이지 완료 증거가 아니다 (`rules/before-work.md`의
  "동작한다로 완료 보고하지 않는다"가 자기 자신에게도 적용된다).

## 판단 로그 — PR 게이트

**스킬 호출 여부와 무관하다.**

**트리거는 상태다(이벤트 아님):** orch 태스크가 `done`이고 그 PR이 열려 있고
**워크트리 `git status --porcelain`이 빈 것**을 확인한 직후. `orch ls`를 직접 친 경우가 여기
포함된다 — orch 완료 알림은 여러 경로 중 하나일 뿐이다.
main/dispatcher 세션에서만 (orch ralph 세션은 헤드리스라 불가). 중복은 PR 번호로 판정 —
장부(위 표)에 그 행이 이미 있으면 skip. 상태 트리거라 여러 번 진입해도 안전해야 한다.

**워크트리가 더러우면 블록을 띄우지 말고 그 사실만 말한다.** orch는 루프가 step 완료를 보고한
시점에 `done`으로 넘어가지만 루프는 그 뒤로도 일한다 — post-PR `review-pr` 지적사항이 추가
커밋으로 얹힌다. 위 `## 완료 신호` 절이 정의한 두 조건이 그대로 여기
적용된다. 알림 시점 사실은 몇 분이면 실제와 어긋난다 (2026-08-06 #89: `done` 이후 커밋 `c589939`·
`a0d3600`, PR #10 생성, 이어서 파일 8개 추가 수정). **이미 바뀐 사실 위에 쌓은 판단은 로그가 없는
것보다 나쁘다** — 틀린 근거가 기록으로 남는다.

main은 워크트리 밖이므로 사실은 직접 모은다 (`gh pr view`,
`git -C <worktree> diff --stat main...HEAD`, PR 본문의 Pre-PR 출력).

**두 층으로 나눈다 — 화면 블록과 상세 파일.** 화면에는 판정에 쓰는 것만 띄우고, 나머지는 상세 파일에 쓴 뒤
화면 맨 아래에 경로 한 줄로 남긴다. 화면 블록은 30줄 안쪽을 목표로 한다.

- 상세 파일: 블록을 쓰는 세션의 scratchpad에 `gate-<ID>-detail.md`로 쓴다. 워크트리에 만들지 않는다(루프나
  `git add`가 커밋에 넣는다). 경로는 `/`로 시작하는 절대 경로 전체를 쓴다
- 상세 파일에 들어가는 것: 규칙·측정값의 정의, 자동 기준 전체 대조, 실패 징후 전부(나타나지 않은 것도 측정값과
  함께), 리뷰가 안 고친 것 전부와 이유 원문, 「확인만 한 것」(CI·테스트·리뷰 건수·변경 범위·도메인 4줄)
- 상세 파일은 화면에서 뺀 것을 잃지 않으려는 곳이다. 줄일 필요가 없다

**화면 블록은 코드 블록이 아니라 마크다운으로 띄운다.** 아래 틀을 ```` ``` ```` 로 감싸지 말고 그대로 출력한다.

```markdown
## <ID> — PR #<n> <title>

- 왜: <이 티켓이 막거나 여는 것을 한 문장으로. 실제 사례 하나를 하위 불릿으로. plan·design 목적 문장에서 가져온다>
- 한 일: <무엇을 바꿨나 한두 문장. 동작을 고르는 규칙이 있으면 하위 불릿으로 한 번만 풀어 쓴다>
  <반려 뒤 재판정이면: 반려 이유(jw 원문), 바꾼 것, 결과를 반려 전 값과 같이 쓴다>

**jw 기준**: 「<jw 원문 그대로>」
- 결과: <그 기준으로 잰 결과를 문장으로. 무엇을 셌는지가 문장 안에 들어간다. 판단어 없이>
- plan 구간: <구간 셋을 문장으로. 어느 구간인지 고르지 않는다>
  - 측정값: <구간 조건에 대응하는 값>

**볼 것**   ← 아래 「볼 것에 올리는 조건」에 걸린 것만. 하나에 한두 문장 + 그 PR의 실제 사례 하나
- <...>
- 나머지(<상세 파일에 무엇이 몇 건 있는지 한 줄>): <상세 파일 절대 경로>

**판정**: ___ 　**이유**: ___
```

**볼 것에 올리는 조건.** 아래 다섯에 걸리면 반드시 올리고, 걸리지 않으면 상세 파일로 보낸다. 무엇을 화면에
띄울지 고르는 것이 반쯤 판정이라 고르는 기준을 Claude 재량에 두지 않는다.

1. 나타났거나 판정할 수 없는 실패 징후
2. 자동 기준 ✗·판정 불가
3. 리뷰 push-back 전부. 지적과 리뷰 세션이 안 고친 이유를 쉬운 말로 쓴다. 이유 원문은 상세 파일에 둔다
4. 데이터를 쓰거나 지우는 won't-fix·defer
5. 결과 숫자를 읽는 법을 바꾸는 사실. 예: 측정이 구현과 같은 규칙을 옮겨 써서 같이 틀릴 수 있다(#90),
   측정 데이터가 규칙을 다듬는 데 쓴 데이터다(#148), 결과의 대부분이 한 종류에서 나왔다(#90 134개 중 121개)

볼 것이 하나도 없으면 「없다」 한 줄을 쓴다. 그때는 jw 기준만 보고 `통과` 한 단어로 판정할 수 있다.

**jw 기준이 「볼 것」보다 위다.** 자동 기준이 10/10이어도 jw 기준이 어긋날 수 있고(#97 — 10/10인데
`impacted 0`), 그게 이 게이트가 잡으려는 것이다. 자동 기준은 ✗가 없으면 화면에 띄우지 않는다.

**「왜」가 맨 위다.** 숫자를 무엇을 보려고 쟀는지 모르면 판정이 안 된다 — 2026-10-06 #69 게이트에서 jw가
「애초에 faq와 현행 법령을 비교한 목적이 뭐였어?」라고 물었다.

**「한 일」이 왜 있나.** PR 내용이 안 잡히면 판정할 재료가 없고, 이유 칸이 안 써지는 가장 흔한 원인이 그것이다
(2026-10-01 jw). 함수·파일 단위 세부는 판정에 거의 안 쓰이고 블록을 길게 만들었다(#101: 5항목 11줄).

**won't-fix·defer도 「무엇이 깨지나」 한 줄은 지우지 않는다.** 상세 파일에 그 한 줄을 둔다. #101 defer #6(설치본이
스캔 대상 프로젝트의 앱 DB에 쓴다)이 그 한 줄로 보였고, 데이터를 쓰는 것이라 조건 4로 화면에 올라온다.

**2026-10-25에 바꿨다.** #101·#136 블록이 각 90줄이었고 jw가 「왜 이렇게 안 읽히나」를 물었다. 원인은 지적받을
때마다 절이 하나씩 붙어(10-01·10-06·10-12) 빠진 것은 없는데 무엇이 중요한지 안 보이게 된 것이었다. 같은
#136을 이 서식으로 다시 쓰니 약 70줄이었고, 늘어난 것은 정의 줄이다.

**2026-10-26에 두 층으로 나눴다.** 10-25 서식으로도 #71은 82줄, #148은 97줄이었다. jw가 「해석이 안 되는 부분도
있고, 길어서 읽는 데 오래 걸려 작업 속도를 떨어뜨린다」고 했다. 설명이 불친절하다는 지적을 고칠 때마다 정의와
설명을 더해 길어졌다 — 두 지적이 반대쪽으로 당겼다. #148을 화면 27줄 + 상세 96줄로 나누니 jw가 「짧아져서
집중도가 높아졌다」고 했다. 같은 날 #90 화면판에서 「깨지는 버전」·「다른 곳」·「아는 값과 「모름」」이 어렵다는
지적을 받았다 — 짧게 쓰려고 붙인 이름이었다. 아래 §쓰는 법의 「이름을 붙이지 않는다」가 그래서 들어갔다.

### 블록을 읽는 법 — jw가 판정할 때

2026-10-12에 다른 세션이 jw에게 알려 준 판단법이다. jw가 「도움이 됐다」고 해서 서식을 이 판단법에
맞췄다 — 예전 「확인할 곳 셋」 절이 그 세 곳이었고, 지금은 화면의 「볼 것」이 그 자리다.

| jw 기준 | 자동 기준 | 보통의 판정 | 쓸 것 |
| --- | --- | --- | --- |
| 충족 | 전부 ✓ | 통과 | `통과` 한 단어 |
| 충족 | ✗ 있음 | 그 ✗에 따라 반려 또는 유보 | 판정 + 이유 한 줄 (왜 그 ✗가 중요한지, 혹은 왜 괜찮은지) |
| 미달 | 전부 ✓ | 반려 또는 유보 | 판정 + 이유 한 줄. 가장 중요한 칸 |
| 못 읽겠다 | — | 유보 | `유보` + 후속 티켓 번호 + 무엇을 다시 잴지 |

- 셋째 줄(jw 기준 미달 + 자동 기준 통과)이 이 장치를 만든 이유다. #97이 이 경우였다
- 반려와 유보 중 고르기 어려우면 「되돌리기 어려운가」만 본다. 어려우면 반려, 아니면 유보 + 후속 티켓
- 「둘 다 충족」인지는 「볼 것」만 훑어 본다. 하나라도 있으면 그걸 받아들이는 이유가 필요하다.
  「없다」면 `통과`만 쓰면 된다

**이 표는 jw가 읽는 법이지 Claude가 판정하는 법이 아니다.** Claude는 표의 어느 줄에 해당하는지 말하지
않는다 — 「jw 기준 충족」이 곧 판정이다(아래 `근거` 칸 규칙).

**판정 순서를 「jw 가판정 → Claude 반론 → 최종」으로 바꾸는 안은 이 서식에 넣지 않았다(2026-10-12).** 반론을 내는
순간 Claude가 판정에 끼는데, 이 로그가 막으려던 것이 그것이다. 판단로그가 다시 안 읽히면 그때 다시 본다.

- **쉬운 말, 사실만.** 파일명·함수명보다 동작으로 쓴다(`judge 단계에 「언급」과 「적용」을 나누는 단계를
  넣었다`). 숫자는 전후를 같이 쓴다(`오탐 0→4건`).
- **판단어를 넣지 않는다.** 개선·안정적·문제없음·잘 동작 같은 말이 들어가면 그 줄이 판정이 된다.
- **게이트에서 jw가 사실을 물으면 사실로만 답한다** (「이 숫자 뭐야?」, 「이 단계는 왜 생겼어?」).
  「그러니 통과가 맞다」 같은 판정 쪽 말은 하지 않는다 — 아래 `근거` 칸 규칙과 같은 이유다.
- 끝까지 내용이 안 잡히면 그것도 판정 재료다 — `유보 / 무엇이 바뀌었는지 이해 못 함 — #NN에서 다시`.

**쓰는 법 — 불릿 하나에 사실 하나, 서술어까지 갖춘 문장으로.**

- **코드 블록에 넣지 않는다.** 코드 블록 안에서는 불릿·굵은 글씨가 안 나오고, 터미널이 줄을 안 바꿔 줘서
  손으로 끊게 된다. 그러면 뜻이 아니라 폭에서 끊긴다(#69 「조·항·호·목 계층을 ⏎ 그대로 둔 채」).
  **줄바꿈은 터미널에 맡긴다.**
- **불릿은 최대 2단계.** 절 이름은 굵게, 사실은 불릿, 같은 사실의 세부는 하위 불릿이다.
- **`→`·`/`로 문장을 잇지 않는다.** 비교도 문장으로 쓴다.
  ```
  ✗ M1 0 vs 임계 ≥3 / M2 16 vs ≥3 → 변형 prompt로 M2를 다시 쟀다 / M2 변형 3
  ✓ - M1에서는 잘린 쿼리가 0건이다
    - M2에서는 잘린 쿼리가 16건이다. 기준(3건 이상)을 넘어서 변형 prompt로 다시 쟀다
    - M2 변형에서는 잘린 쿼리가 3건이다. 기준이 3건 이상이라 여전히 기준에 걸린다
  ```
  ✗ 쪽은 마지막 값(3건)이 여전히 기준에 걸린다는 사실을 줄이면서 지웠다. **줄이는 것은 증거를 지우는
  것이고, 그건 이 로그의 목적과 반대다.**
- **화면에서는 측정값이나 개념에 이름을 붙이지 않는다. 무엇을 셌는지 문장으로 쓴다.** 정의 절을 두지 않는 대신
  정의가 필요 없게 쓴다. jw는 plan을 펴 놓고 블록을 읽지 않는다.
  ```
  ✗ 깨지는 버전이 134/134 지점에 붙었고 다른 곳은 0이다
  ✓ 버전을 적어야 하는 코드 줄 134개 모두에 「Django 몇 버전에서 깨짐」이 적혔다.
    측정 스크립트가 DB로 따로 다시 계산해 맞춰 보니 다르게 적힌 줄은 0개였다
  ```
  - plan·코드의 줄임말(`M1`·`tp`·`R`·`D`)과 plan이 정한 말(`both`·`회차`)을 화면에 쓰지 않는다. 정의는 상세 파일에 둔다
  - 풀어 쓴 말을 낫표로 감싸 다시 부르지 않는다. 「다르게 적힌 줄」을 두 번째부터 이름처럼 쓰면 그것도 이름이다
  - 원어를 그대로 써도 되는 것은 둘뿐이다: jw 기준 원문에 있는 말, 도구·리포트·DB에 실제로 찍히는 글자
    (`removed`·「제거 버전 모름」 등). 처음 나올 때 한 번 풀어 쓴다

### 흐름 그림 — 실행 흐름이 바뀐 PR에만 붙인다

PR이 **실행 순서·단계·분기 조건·데이터가 지나가는 경로**를 바꿨으면 블록을 띄운 뒤 `archify`로
흐름 그림 한 장을 만들어 경로를 알려 준다. 문구 수정·버그 한 줄·테스트 추가처럼 흐름이 그대로인
PR에는 그리지 않는다 — 그릴 것이 없고 게이트만 느려진다.

**왜.** 2026-10-12 jw — 판단 로그를 읽어도 「무엇이 바뀌었는지」가 안 잡히는 때가 있다. 「이 PR이 한 일」
세 줄은 바뀐 단계를 문장으로 늘어놓을 뿐이라 전·후 흐름이 머리에 안 그려진다. 머지된 PR 하나로 먼저
그려 봤고 jw가 「도움 된다」고 했다.

- **종류는 `workflow`.** 변경 후 흐름 한 장에 노드마다 꼬리표(`tag`)를 단다: `새로 생김` · `조건 바뀜` ·
  `주기 바뀜` · `범위 좁아짐` · `그대로` · `없어짐`. 없어진 단계는 `없어짐`을 달아 맨 아래 별도
  줄(`variant: exception`)에 두고, 대신 들어온 노드로 「이걸로 바뀜」 화살표를 긋는다. 바뀌지 않은 구간은
  노드 하나로 접는다.
  - **없어진 단계인지는 줄이 아니라 `없어짐` 꼬리표로 구별한다.** `variant: exception` 줄에는 실패 경로도
    그린다. work-board 흐름 탭은 `없어짐`이 달린 노드만 빨간 테두리로 그린다. 2026-10-20 회사 PR 그림에서
    실패 경로 줄의 `[그대로]` 노드가 없어진 단계처럼 빨갛게 나왔다.
- **근거를 단다.** 노드마다 `sources`(파일·줄)를 걸고 `meta.repository`에 PR head 커밋을 박는다.
  `finalize`에 `--repo-root <워크트리>`를 준다. 그림은 Claude의 해석이라, 줄 번호가 없으면 블록의 사실
  줄과 같은 무게로 읽힐 근거가 없다.
- **경로는 `/`로 시작하는 절대 경로 전체를 쓴다.** `scratchpad/...`처럼 줄이면 iTerm2에서 ⌘+클릭으로
  안 열린다. 백틱·괄호로 감싸지 말고 앞뒤를 띄운다 — 붙은 글자까지 경로로 잡힌다.
- **블록을 대신하지 않는다.** 블록이 먼저고 그림은 그 뒤에 경로 한 줄이다. 판정은 여전히 블록의 사실과
  jw 기준으로 한다 — 그림이 잘못 단순화됐으면 틀린 근거가 되므로, 그림과 블록이 어긋나면 블록을 따른다.
- **저장은 로컬 scratchpad.** `.archify/`를 워크트리에 만들면 루프나 `git add`가 커밋에 넣는다. 회사 코드
  구조가 담기므로 claude.ai 아티팩트로 올리지 않는다.
- **자동 검사를 통과 못 해도 그림은 낸다.** 한 번 고쳐서도 `finalize`가 실패하면 더 고치지 않고 같은
  candidate로 `render`를 돌린다. `render`는 검사(`validate`의 가독성·폭 검사 등)를 건너뛰고 HTML을 쓴다.
  ```bash
  node <archify>/bin/archify.mjs render workflow <candidate.json> <out.html> --repo-root <워크트리>
  ```
  블록 뒤에 경로 한 줄과 실패한 검사 이름·값을 같이 적는다(`흐름 그림: <절대 경로> — archify 검사 실패
  (composition/desktop-readability, 폭 1367px vs 기준 961px)`). 그림 때문에 게이트를 붙잡지 않는다.
  - 2026-10-13 회사 PR 게이트에서 폭 검사만 걸려 그림이 생략됐다. jw가 「무시하고 출력되도록」 하라고 했다 —
    글자가 작게 나와도 흐름은 읽힌다.

## jw 기준의 출처 — plan, 게이트에서 새로 묻지 않음

`jw 기준`은 plan 맨 위 `## jw 기준`에서 원문 그대로 가져온다. 받는 절차는
`rules/before-work.md` §착수 전 한 줄. PR 게이트에서 묻거나 다듬지 않는다.

**plan에 `## jw 기준`이 없으면 그 사실을 첫 줄에 적는다** (`jw 기준: plan에 없음`). 지어내지
말 것. Kickoff가 놓친 것이고, 그 기록이 다음 Kickoff를 고치게 한다. 2026-09-30 이전 plan은
전부 이 경우다.

**어긋났는지 판정은 jw가 한다.** 결과가 기준에 걸리는지 경계 사례가 있고, 후하게 세는 것이
이 기록의 유일한 실패 방식이다. jw 기준 아래 불릿에는 값만 적는다.

이전 방식(착수 전 예측 3개 → 적중 `n/3` → 놓친 것)은 2026-09-30에 걷어냈다. 이유는
`rules/before-work.md` §착수 전 한 줄.

**위 블록은 그 plan에서 온다.** 「확인만 한 것」 줄은 어느 티켓에나 똑같이 붙어서, 그것만 보면
이 티켓이 **무엇을 달성했어야 하는지**를 알 수 없다 — 백지에서 판정하게 되고, 실사용에서
막힌 지점이 정확히 여기였다. 판단은 착수 전 plan에 이미 문장으로 적혀 있으므로
(`rules/before-work.md`) PR 게이트는 **새 판단을 내리는 자리가 아니라 이미 내린 판단을
대조하는 자리**다. 사전 기준을 왼쪽, 사후 증거를 오른쪽에 나란히 놓아야 대조가 성립한다.

증거는 **위치**로 적는다 (`VERIFICATION.md:169-176`, 커밋 `a0d3600`, `543 passed`).
"확인함" / "충족" / "문제 없음"은 증거가 아니라 판정이다 — 아래 첫 번째 규칙 위반이다.

실패 징후는 **측정값과 plan 임계값을 나란히** 적는다. 나타났는지 여부만 적으면 읽는 쪽이
그 판정을 검증할 수 없다.
(실례 — #89 plan: *"`unknown`이 0건이면 의심한다"* → 실제 `unknown` 0건 →
`SYMBOLS_VERIFICATION.md:169-176`에서 코드 경로 + 전수 42건으로 해명.)

**plan 징후에 임계값이 없으면 `판정 불가`로 적는다.** 측정값만 적고 나타남/없음을 고르지
말 것 — 그 선택이 곧 판정이고, 근거가 없다. #91이 이 경우다: plan은 *"뭉침이 재현되면
의심"*, 실제는 `spread 0.1626`. 재현 안 됨이 통과인지 측정 실패인지 plan이 정의하지 않았다.
`판정 불가`가 그대로 `유보` 사유가 되고, 다음 Kickoff에서 그 임계값을 못 박고 들어간다.

plan에 통과 기준·실패 징후가 **비어 있으면 그 사실을 첫 줄에 적는다**
(`통과 기준: plan에 없음 — 대조 불가`). 대신 지어내지 말 것. 빈 plan으로 무인 실행한 것은
Kickoff 게이트가 놓친 것이고, 그 기록이 다음 plan을 고치게 한다.

**출처를 반드시 표기한다.** 7줄 중 5줄이 루프가 쓴 텍스트(PR 본문)에서 온다. Pre-PR 체크는
completion-promise지 하드 게이트가 아니므로, 검증 안 된 주장을 사실 칸에 그냥 적으면 이 로그는
루프의 자기보고를 그대로 승인하는 도장이 된다. 구분이 보이게 쓸 것:

```
  테스트       557 passed (PR 본문 주장, CI 미확인)
  테스트       557 passed (CI checks green)
```

`CI 체크`는 `gh`가 GitHub에서 직접 읽는 값이라 루프가 건드릴 수 없다 — 유일하게 독립적인 줄이다.
둘이 어긋나면 그 자체가 가장 중요한 사실이다.

**리뷰가 안 고친 것과 리뷰 건수 줄은 Phase C 리뷰 세션이 쓴 파일에서 온다** — 구현 세션이 아니라 그 코드를 쓰지
않은 세션이 쓴 것이라 자기보고가 아니다. 그래도 판정이 아니라 **사실**로 옮긴다: `push-back`을
정당한 반론으로 볼지는 jw가 정한다. `push-back`·`won't-fix` 행이 있으면 그 이유를 상세 파일에 그대로 옮겨
적을 것 — 개수만 적으면 판정할 수 없다.

- 사실은 **값**이지 판정이 아니다. 안전함 / 문제없음 / 위험해보임 금지. `DROP COLUMN`과
  `롤백 절차 없음`은 사실로 적고, 그게 결격인지는 jw가 정한다.
- **수치에는 비교 대상을 반드시 붙인다.** 절대값 하나만 적으면 읽는 쪽이 판정할 수 없다.
  2026-08 로그 4행을 전수로 보면 **해석된 줄은 예외 없이 값이 둘인 줄**이었다:

  | 로그에 적힌 것 | 판정 가능? |
  | --- | --- |
  | `spread 0.1626로 퍼짐` | **불가** — 0.16이 좋은지 나쁜지 모름 |
  | `unknown 0건` | **불가** — 정상인지 파서가 죽은 건지 모름 |
  | `API호출 6 < 516` | 가능 |
  | `로컬 651 passed vs PR본문 645` | 가능 |

  비교 대상은 순서대로 **plan §실패 징후의 임계값 → 직전 티켓 측정값 → baseline**.
  셋 다 없으면 `(baseline 없음 — 첫 측정)`이라고 명시한다. **"비교 불가"도 판정
  재료다** (→ `유보`).
- **`✓`는 기계적으로 확인되는 기준에만 붙인다.** `테스트 통과` · `파일 존재` · `컬럼 추가됨`
  → ✓ 가능. **`precision이 baseline보다 낫다` · `뭉침이 해소됐다` → 값만 적고 ✓ 금지.**
  후자에 ✓를 붙이는 순간 그건 사실이 아니라 판정이고, 채점이 끝난 답안지를 주고 채점하라는
  꼴이 된다 — 남는 행동이 통과 누르기뿐이다. `기준 5/5 ✓`가 4행 내내 그랬다.
- **판정은 3택 — 통과 / 반려 / 유보. 판정마다 다음 행동이 하나로 정해져 있다.**

  | 판정 | 뜻 | PR | 다음 |
  | --- | --- | --- | --- |
  | 통과 | 결과를 받아들인다 | 머지 | 끝 |
  | 반려 | 이대로는 안 받는다 | 머지 안 함 | jw가 고른다: ① 같은 PR에서 고친다(plan에 Task 추가 → 루프 다시) ② PR을 닫고 티켓을 되돌린다. 기본값 없음 — 반려 직후 한 번 묻는다. `★ADR후보` 태그 — 주 1회 그중 하나를 ADR로 올린다 |
  | 유보 | 지금 정보로는 못 정한다 — 기준이 결과를 못 읽었거나, 미달인데 받아들일 대가인지 모른다 | 머지해도 된다 | **후속 티켓 필수.** 무엇을 어느 티켓에서 다시 잴지 정하고, 이유 칸에 그 번호를 적는다 |

  **후속 티켓 없는 유보는 조용한 통과다.** #91이 그렇게 접혔다 — plan이 *"뭉침이 재현되면 의심"*이라
  `spread 0.1626`을 못 읽었는데 2택이라 통과로 기록됐다. 유보에 번호가 없으면 받지 말고 되묻는다.

  유보를 머지 가능으로 둔 이유 — 머지를 미루면 PR이 몇 주씩 열려 있고, 그동안 다음 티켓이 이 코드
  위에 못 올라간다. **되돌리기 어려운 변경(스키마·데이터 삭제)이면 유보가 아니라 반려다.**

  후속 티켓에서 다시 잰 뒤 **원래 행을 고치지 않는다.** 후속 티켓 행의 이유 칸에
  `#96 유보 → 통과`처럼 이어서 적는다. 판단이 바뀐 이력 자체가 기록이다.
- **근거를 제안하거나 대신 채우지 말 것.** 그 빈칸이 유일하게 사람 몫이라 이 로그가 존재한다.
  채워주는 순간 로그가 Claude의 추론이 되고, 그건 이 로그가 막으려던 바로 그것이다.
- jw가 한 단어로 답한다 (`통과`). 갈렸으면 이유 한 줄을 붙인다 (`유보 / tp 3건 잃은 게 대가인지 #100에서 다시 본다`)
  → 장부에 적는다.
  - `~/prv`: PR 브랜치에서 `docs/decisions.md`의 그 티켓 행(Kickoff 때 기준 칸만 채워 둔 것)에
    결과·판정·이유를 채우고, README `## 판단 기록` 절도 고쳐 커밋·push한다. 판정이 코드와 같이
    머지된다. 서식은 `rules/before-work.md` §레포에 남기는 판단 기록.
  - 회사: `~/.claude/judgment-log-work.md`에 아래 7열 한 행을 append한다.
- **블록 → 표 한 줄로 접는 규칙 (회사 장부).** `judgment-log-work.md`는
  `| 날짜 | 티켓 | jw 기준 | 결과 | 판정 | 본 것 (사실) | 근거 |` 7열이다.
  `jw 기준`은 원문 그대로, `결과`는 그 기준으로 잰 값 한 줄. plan에 없으면 둘 다 `—`.
  `본 것` 칸에는 **자동 기준 요약 + 나타난 징후만** 적는다:
  `자동 5/5 ✓ · ⚠unknown 0 vs 임계 >0(VERIFICATION.md:169)` / `자동 3/5 ✓, 4번 미측정 · 징후 없음`.
  **수치는 표에서도 비교 대상을 떼지 않는다** — 떼는 순간 나중에 다시 읽을 때 해석이 안 된다.
  나타나지 않은 징후와 「확인만 한 것」 줄은 칸에서 뺀다 — 블록은 판단할 때 보는 화면이고 표는 나중에 다시
  읽는 기록이라, 표에 남길 것은 **판정을 가른 것**뿐이다. CI와 PR 본문이 어긋났으면 그건 판정을
  가른 사실이므로 남긴다 (`테스트 557 주장 vs CI red`). 형식이 흔들리면 시계열 비교가 죽으므로
  이 축약형을 벗어나지 말 것.
- `스킵` → 판단 칸을 빈 채로 append. 빈칸도 데이터다(그날 게이트가 형식이었다는 기록). 재촉 금지,
  나중에 채우지도 말 것.
- 여러 건 동시 완료 → 압축해 나열하고 한 줄로 전부 받는다
  (`7133 통과 롤백리스크없음 / 7150 반려 드롭컬럼 롤백없음 / 7161 스킵`). 파싱은 Claude 몫.
- 순서: **판단 먼저, 티켓 정리 나중.** diff가 신선할 때 판단하고, 정리는 잡무다.
