# 판단 기록

**여기 있는 이유 — 항상 컨텍스트에 있어야 하기 때문이다.** 이 규칙들이 `dev-workflow`
스킬 안에만 있던 동안 한 번도 뜨지 않았다. 스킬은 호출해야 로드되고, 임의 PR 리뷰
세션(`ops:github-pr-review` 등)은 자신이 "게이트"에 있다고 인식하지 않는다.

개발 파이프라인 자체는 `dev-workflow` 스킬에 있다. 이 파일은 **판단을 기록하는 두 지표**만
담는다 — 판단 로그(PR 게이트), 문제 발견(상시).

## 완료 신호 — 판단 로그 트리거의 전제

**완료 판정 = `orch ls`가 `done` + 워크트리 `git status --porcelain`이 빈 것.**
PR URL이나 Notion `PR` 컬럼이 찼다고 완료가 아니다.

- ralph 루프는 **PR을 만든 뒤에도 계속 일한다.** 커밋 전 `superpowers:requesting-code-review`,
  PR 생성 후 `pr-review-toolkit:review-pr`을 돌려 지적사항을 추가 커밋으로 얹는다.
  실측: PR 생성 후 8분 넘게 작업 지속.
- orch가 `running`인 동안 PR을 리뷰하지 말 것 — 리뷰 도중 커밋이 얹혀 대상이 어긋난다.
- **산출물이 그럴듯할수록 확인을 건너뛰기 쉽다.** PR 본문에 테스트 수와 통과 기준 표가
  있어도 그건 루프의 주장이지 완료 증거가 아니다 (`rules/portfolio-judgment.md`의
  "동작한다로 완료 보고하지 않는다"가 자기 자신에게도 적용된다).

## 판단 로그 — PR 게이트

**스킬 호출 여부와 무관하다.**

**트리거는 상태다(이벤트 아님):** orch 태스크가 `done`이고 그 PR이 열려 있고
**워크트리 `git status --porcelain`이 빈 것**을 확인한 직후. `orch ls`를 직접 친 경우가 여기
포함된다 — orch 완료 알림은 여러 경로 중 하나일 뿐이다.
main/dispatcher 세션에서만 (orch ralph 세션은 헤드리스라 불가). 중복은 PR 번호로 판정 —
`~/.claude/judgment-log.md`에 그 행이 이미 있으면 skip. 상태 트리거라 여러 번 진입해도 안전해야 한다.

**워크트리가 더러우면 블록을 띄우지 말고 그 사실만 말한다.** orch는 루프가 step 완료를 보고한
시점에 `done`으로 넘어가지만 루프는 그 뒤로도 일한다 — post-PR `review-pr` 지적사항이 추가
커밋으로 얹힌다. 위 `## 완료 신호` 절이 정의한 두 조건이 그대로 여기
적용된다. 알림 시점 사실은 몇 분 만에 낡는다 (2026-08-06 #89: `done` 이후 커밋 `c589939`·
`a0d3600`, PR #10 생성, 이어서 파일 8개 추가 수정). **낡은 사실 위에 쌓은 판단은 로그가 없는
것보다 나쁘다** — 틀린 근거가 기록으로 남는다.

main은 워크트리 밖이므로 사실은 직접 모은다 (`gh pr view`,
`git -C <worktree> diff --stat main...HEAD`, PR 본문의 Pre-PR 출력).

```
<ID> — PR #<n> <title>

통과 기준 (plan §통과 기준)         → 대조 결과
  1 <기준 문장 그대로>               <증거 위치. 파일:줄 / 커밋 / 수치>   [✓|✗ — 기계 확인만]
  2 ...                             ...
  (plan에 있는 항목 전부. 빼지 말 것)

실패 징후 (plan §실패 징후)
  ⚠|· <징후 문장 그대로>             <측정값> vs <plan 임계값> → 나타남|없음|판정 불가

착수 전 예측 (plan §착수 전 예측)
  1 <예측 키워드>                    걸림|안 걸림. <걸렸으면 증거 위치>
  2 ...
  (plan이 `skip`이면 이 절 통째로 생략)

검증 출력 (사실)
  CI 체크      <gh pr view --json statusCheckRollup 결과. 체크 없으면 "없음">
  테스트       <pass/fail 숫자 + 출처. 출력 없으면 "출력 없음">
  변경 범위     <n files, +a −b>   (계획: <m> files)
  리뷰 처리     Critical <n> → fix <a> / push-back <b>, Important <n> → fix <a>
               (docs/plans/<ID>-MMDD-review-<topic>.md. Phase C 없이 왔으면 "리뷰 세션 없음")
  <도메인 4줄 — 아래 표에서 티켓 성격에 맞는 묶음을 고른다>

판단 (비워둠)
  예측 적중 : ___ / 3        (plan 예측이 `skip`이면 —)
  놓친 것   : ___            (예측에 없던 것 하나. 전부 맞혔으면 없음)
  통과/반려/유보 : ___
  근거      : ___
```

**도메인 4줄 — 티켓 성격에 맞춰 고른다.**

| 티켓 성격 | 4줄 |
| --- | --- |
| 백엔드·API | 서버 부팅 / 신규 env / 마이그레이션 / 롤백 절차 |
| RAG·검색·eval | 검색 품질 (baseline 대비) / 평가셋 (질문 N개 + 출처) / 비용 (호출·토큰·$) / 재현성 (같은 쿼리 2회 = 같은 결과인가) |
| 데이터 파이프라인 | 처리 건수 (입력→출력, 유실 N) / 실패 격리 (N건 + 사유) / 재실행 안전성 (멱등인가) / 소요 시간 |

**고정 7줄이던 것을 바꾼 이유.** 2026-08 판단 로그 4행 전부에서 `서버 부팅 N/A` ·
`마이그레이션 없음` · `롤백 없음` · `CI 없음`이 나왔다 — 7줄 중 4줄이 매번 빈 줄이었다.
`~/prv`는 RAG 레포인데 서식은 백엔드 티켓용이라, **정작 판정을 가른 검색 품질 수치는 칸이
없어서 `⚠` 뒤에 산문으로 끼어 있었다.** 표가 신호를 밀어냈다.

## 예측은 여기서 묻지 않는다 — Kickoff에서 이미 받았다

`착수 전 예측` 절은 **plan 문서에서 읽어 온다.** PR 게이트에서 새로 묻지 않는다.
받는 절차는 `rules/portfolio-judgment.md` §착수 전 예측.

**여기서 물으면 안 되는 이유.** 예측을 이 자리에서 받으려면 diff를 먼저 보여줘야 하는데
그게 곧 답이다. 그래서 예전 서식은 "1단계(파일·심볼만) → 답 → 2단계(사실)"로 두 번 말했고,
2026-08-19~08-26 사이 기회 1번에 기록 0건이었다. 시점 자체가 틀렸다 — orch 완료 알림은
밤에 뜨고, 앉아서 추론할 자리가 아니다.

**plan에 `착수 전 예측`이 없으면 그 사실을 적는다** (`착수 전 예측: plan에 없음`).
지어내지 말 것. Kickoff 게이트가 놓친 것이고, 그 기록이 다음 Kickoff를 고치게 한다.

**겹쳤는지 판정은 jw가 한다.** 표현이 다른 같은 문제인지는 경계 사례가 있고, 후하게
세는 것이 이 지표의 유일한 실패 방식이다. 네가 세지 말고 물어라.

**사후에 채우지 말 것.** plan이 `skip`인 날은 `—`가 맞는 값이다. `근거` 칸은 판단이라
검증 대상이 아니지만 **적중률은 숫자라서 다르다** — 자기기만이 그대로 통계로 굳는다.

이 지표의 출처는 TDR 「구현에서 손을 떼되 감각은 측정한다」다.

**위 블록은 그 plan에서 온다.** 검증 출력 줄은 어느 티켓에나 똑같이 붙어서, 그것만 보면
이 티켓이 **무엇을 달성했어야 하는지**를 알 수 없다 — 백지에서 판정하게 되고, 실사용에서
막힌 지점이 정확히 여기였다. 판단은 착수 전 plan에 이미 문장으로 적혀 있으므로
(`rules/portfolio-judgment.md`) PR 게이트는 **새 판단을 내리는 자리가 아니라 이미 내린 판단을
대조하는 자리**다. 사전 기준을 왼쪽, 사후 증거를 오른쪽에 나란히 놓아야 대조가 성립한다.

증거는 **위치**로 적는다 (`VERIFICATION.md:169-176`, 커밋 `a0d3600`, `543 passed`).
"확인함" / "충족" / "문제 없음"은 증거가 아니라 판정이다 — 아래 첫 번째 규칙 위반이다.

실패 징후는 **측정값과 plan 임계값을 나란히** 적는다. 나타났는지 여부만 적으면 읽는 쪽이
그 판정을 검증할 수 없다.
(실례 — #89 plan: *"`unknown`이 0건이면 의심한다"* → 실제 `unknown` 0건 →
`SYMBOLS_VERIFICATION.md:169-176`에서 코드 경로 + 전수 42건으로 해명.)

**plan 징후에 임계값이 없으면 `판정 불가`로 적는다.** 측정값만 적고 나타남/없음을 고르지
말 것 — 그 선택이 곧 판정이고, 근거가 없다. #91이 이 경우다: plan은 *"뭉침이 재현되면
의심"*, 실제는 `spread 0.1626`. 재현 안 됨이 통과인지 측정 실패인지 plan이 정의하지 않았다.
`판정 불가`가 그대로 `유보` 사유가 되고, 다음 Kickoff에서 그 임계값을 못 박고 들어간다.

plan에 통과 기준·실패 징후가 **비어 있으면 그 사실을 첫 줄에 적는다**
(`통과 기준: plan에 없음 — 대조 불가`). 대신 지어내지 말 것. 빈 plan으로 무인 실행한 것은
Kickoff 게이트가 놓친 것이고, 그 기록이 다음 plan을 고치게 한다.

**출처를 반드시 표기한다.** 7줄 중 5줄이 루프가 쓴 텍스트(PR 본문)에서 온다. Pre-PR 체크는
completion-promise지 하드 게이트가 아니므로, 검증 안 된 주장을 사실 칸에 그냥 적으면 이 로그는
루프의 자기보고를 그대로 승인하는 도장이 된다. 구분이 보이게 쓸 것:

```
  테스트       557 passed (PR 본문 주장, CI 미확인)
  테스트       557 passed (CI checks green)
```

`CI 체크`는 `gh`가 GitHub에서 직접 읽는 값이라 루프가 건드릴 수 없다 — 유일하게 독립적인 줄이다.
둘이 어긋나면 그 자체가 가장 중요한 사실이다.

**`리뷰 처리` 줄은 Phase C 리뷰 세션이 쓴 파일에서 온다** — 구현 세션이 아니라 그 코드를 쓰지
않은 세션이 쓴 것이라 자기보고가 아니다. 그래도 판정이 아니라 **사실**로 옮긴다: `push-back`을
정당한 반론으로 볼지는 jw가 정한다. `push-back`·`won't-fix` 행이 있으면 그 이유를 그대로 옮겨
적을 것 — 개수만 적으면 판정할 수 없다.

- 사실은 **값**이지 판정이 아니다. 안전함 / 문제없음 / 위험해보임 금지. `DROP COLUMN`과
  `롤백 절차 없음`은 사실로 적고, 그게 결격인지는 jw가 정한다.
- **수치에는 비교 대상을 반드시 붙인다.** 절대값 하나만 적으면 읽는 쪽이 판정할 수 없다.
  2026-08 로그 4행을 전수로 보면 **해석된 줄은 예외 없이 값이 둘인 줄**이었다:

  | 로그에 적힌 것 | 판정 가능? |
  | --- | --- |
  | `spread 0.1626로 퍼짐` | **불가** — 0.16이 좋은지 나쁜지 모름 |
  | `unknown 0건` | **불가** — 정상인지 파서가 죽은 건지 모름 |
  | `API호출 6 < 516` | 가능 |
  | `로컬 651 passed vs PR본문 645` | 가능 |

  비교 대상은 순서대로 **plan §실패 징후의 임계값 → 직전 티켓 측정값 → baseline**.
  셋 다 없으면 `(baseline 없음 — 첫 측정)`이라고 명시한다. **"비교 불가"도 판정
  재료다** (→ `유보`).
- **`✓`는 기계적으로 확인되는 기준에만 붙인다.** `테스트 통과` · `파일 존재` · `컬럼 추가됨`
  → ✓ 가능. **`precision이 baseline보다 낫다` · `뭉침이 해소됐다` → 값만 적고 ✓ 금지.**
  후자에 ✓를 붙이는 순간 그건 사실이 아니라 판정이고, 채점이 끝난 답안지를 주고 채점하라는
  꼴이 된다 — 남는 행동이 통과 누르기뿐이다. `기준 5/5 ✓`가 4행 내내 그랬다.
- **판정은 3택 — 통과 / 반려 / 유보.** `유보`는 "기준값이 없어 판정 불가"다.
  #91의 실제 상태가 그것이었는데 2택이라 통과로 접혔다. **유보가 기록돼야 다음 plan의
  §실패 징후가 고쳐진다** — 유보로 적힌 항목은 다음 Kickoff에서 임계값을 못 박고 들어간다.
- **근거를 제안하거나 대신 채우지 말 것.** 그 빈칸이 유일하게 사람 몫이라 이 로그가 존재한다.
  채워주는 순간 로그가 Claude의 추론이 되고, 그건 이 로그가 막으려던 바로 그것이다.
- jw가 한 줄로 답한다 (`통과 / 롤백 리스크 없음`) → 그 행을 `~/.claude/judgment-log.md`에 append.
- **블록 → 표 한 줄로 접는 규칙.** 로그는
  `| 날짜 | 티켓 | 예측 (착수 전) | 적중 | 놓친 것 | 판정 | 본 것 (사실) | 근거 |` 8열이다.
  `예측`은 plan §착수 전 예측의 3개를 키워드로 줄여 넣고 (`N+1, 트랜잭션 경계, 타임존`),
  `적중`은 `2/3`. plan이 `skip`인 날은 세 칸 다 `—`.
  위 블록 전체를 넣지 말고 `본 것` 칸에는 **기준 요약 + 나타난 징후만** 적는다:
  `기준 5/5 ✓ · ⚠unknown 0 vs 임계 >0(VERIFICATION.md:169)` / `기준 3/5 ✓, 4번 미측정 · 징후 없음`.
  **수치는 표에서도 비교 대상을 떼지 않는다** — 떼는 순간 나중에 다시 읽을 때 해석이 안 된다.
  나타나지 않은 징후와 검증 출력 7줄은 칸에서 뺀다 — 블록은 판단할 때 보는 화면이고 표는 나중에 다시
  읽는 기록이라, 표에 남길 것은 **판정을 가른 것**뿐이다. CI와 PR 본문이 어긋났으면 그건 판정을
  가른 사실이므로 남긴다 (`테스트 557 주장 vs CI red`). 형식이 흔들리면 시계열 비교가 죽으므로
  이 축약형을 벗어나지 말 것.
- **`놓친 것` — 이 칸이 유일한 학습 신호다.** `2/3` 이라는 숫자에는 배울 게 거의 없다.
  배우는 것은 **빗나간 항목이 왜 안 보였는가**이고, 그건 2단계 블록을 본 직후 그 자리에서만
  또렷하다. 리뷰에서 나왔는데 예측에 없던 것 **하나**를 키워드로 적는다 (`타임존 경계`).
  전부 맞혔으면 `없음`, 1단계를 건너뛴 날은 `—`.
  **후보를 대신 대지 말 것.** 위 `근거` 칸과 같은 이유다 — 무엇을 놓쳤는지 고르는 것이 이
  칸의 전부라서, 내가 목록을 내밀면 jw는 고르기만 하게 되고 칸이 죽는다. jw의 한 줄 답에
  섞여 오면(`통과 / 롤백리스크없음 / 놓침: 타임존`) 파싱은 Claude 몫이다.
  **사후에 채우지 않는다.** `적중`과 같은 이유로 자기기만이 그대로 통계가 된다.
- `스킵` → 판단 칸을 빈 채로 append. 빈칸도 데이터다(그날 게이트가 형식이었다는 기록). 재촉 금지,
  나중에 채우지도 말 것.
- 반려 → `★ADR후보` 태그. 주 1회 그중 하나를 정식 ADR로 승격.
- 여러 건 동시 완료 → 압축해 나열하고 한 줄로 전부 받는다
  (`7133 통과 롤백리스크없음 / 7150 반려 드롭컬럼 롤백없음 / 7161 스킵`). 파싱은 Claude 몫.
- 순서: **판단 먼저, 티켓 refine 나중.** diff가 신선할 때 판단하고, refine은 행정이다.

## 문제 발견 — 게이트가 아니라 상시 캡처다

같은 파일의 `## 문제 발견 (주 1건)` 표. 티켓으로 만들어지지 않았는데 고쳐야 할 것을 적는다.
TDR 「구현에서 손을 떼되 감각은 측정한다」의 지표 2번.

**트리거는 jw의 한 마디다.** `문제 발견: <내용>` 이라고 하면 `~/.claude/judgment-log.md`의
`## 문제 발견` 표에 이번 ISO 주차(`date +%G-W%V`) 행을 append한다. **세션 종류·디렉터리 무관** —
dev-workflow 안이든 밖이든, 업무 repo든 `~/prv`든 똑같이 받는다. `티켓화` 칸은 비워두고
(`안 함`), 나중에 티켓이 생기면 그때 채운다.

**PR 게이트에 붙이지 않는다.** 게이트는 PR마다 열리는데 이건 주 단위이고, 더 중요하게는
게이트가 **티켓 작업 한복판**이라 거기서 물으면 떠오르는 것이 전부 그 티켓 언저리가 된다.
찾으려는 것이 "티켓이 없는 것"인데 티켓 문맥 안에서 묻는 셈이다.

**금요일 잡(`~/prv/jobs`의 `problem-found`)은 점검이지 캡처가 아니다.** 행이 있나 없나만
보고 Notion으로 알린다. 문제는 금요일 18:43에 발견되지 않는다 — 화요일 오후에 지나가고,
금요일에 회상하려 하면 안 떠오른다. 그래서 캡처는 상시고 잡은 안전망이다.

주 1건은 상한이 아니라 하한이다. 한 주에 셋이면 셋 다 넣는다 — 잡은 "하나라도 있나"만 본다.

**내용을 제안하지 말 것.** 위 `근거` 칸과 같은 이유다. 무엇이 문제인지 고르는 것이 이 지표의
전부라서, 후보를 내가 대면 지표가 죽는다. 금요일 잡을 `run: claude`가 아니라 `run: script`로
둔 것도 같은 이유 — 제안할 수 있는 주체를 아예 두지 않았다.
